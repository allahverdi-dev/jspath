# Localization

JSPath's interface is available in English, Azerbaijani and Russian. This
describes how that works and how to add to it.

---

## 1. Two layers, kept separate

| Layer | What it covers | Localized? |
| --- | --- | --- |
| **Product UI** | navigation, buttons, labels, settings, billing status, errors, empty states, accessibility names | **Yes** — en, az, ru |
| **Authored learning content** | lesson prose, challenge statements, project briefs, interview questions, Reference entries, Cheat Sheets, teaching diagrams | **No** — English, and canonical |

These are deliberately different systems. The dictionaries under `src/i18n/`
hold interface strings only; the learning libraries under `src/content/` are
authored English and are validated by `content:audit`, `content:verify` and
`content:examples`.

Because the content is still English, the language selector says so plainly
(`settings.languageHint`) rather than implying a translation that does not
exist. If authored content is translated later, that note is what changes.

---

## 2. Supported locales

| Code | Name shown | `Intl` tag |
| --- | --- | --- |
| `en` | English | `en` |
| `az` | Azərbaycan dili | `az-AZ` |
| `ru` | Русский | `ru-RU` |

English is the default and the fallback. A saved preference that is missing,
unrecognised or unsupported resolves to English rather than leaving the
interface half-translated.

The browser's language is **not** used to switch automatically. English is the
declared product default, and silently flipping a returning learner into another
language because of their OS setting is worse than asking. The choice is
explicit, in Settings.

---

## 3. Architecture

No i18n dependency was added. The app ships five production packages, and what a
library would contribute here is key lookup, interpolation and plural selection.
The first two are a few lines. The third is the part worth getting right, and the
platform already does it better than a hand-written rule table would:

- `Intl.PluralRules` chooses the plural category
- `Intl.DateTimeFormat` formats dates
- `Intl.NumberFormat` formats numbers
- `Intl.ListFormat` joins lists ("Foundations, Async and Engineering")

```
src/i18n/
  core.js              lookup, interpolation, plural selection, formatters
  index.jsx            I18nProvider, useI18n, useT
  i18n.test.js         dictionary validation
  locales/
    en.js              canonical
    az.js
    ru.js
```

**912 strings across 31 namespaces**, grouped by product surface — the largest
being learning (113), billing (80), achievements (63), dashboard (59),
interview (57), placement (48) and common (47). Russian has more entries than
the other two (952) because its counted strings carry `few` and `many` forms.

All three dictionaries are bundled. They are small, and lazy-loading them would
trade a couple of kilobytes for a loading state on every language switch.

## 4. Using it

```jsx
import { useT, useI18n } from '../i18n/index.jsx';

const t = useT();
t('nav.dashboard');                          // "Dashboard"
t('common.xp', { count: 40 });               // "40 XP"
t('common.lessonCount', { count: 5 });       // "5 lessons" / "5 dərs" / "5 уроков"

const { locale, setLocale, formatDate, formatNumber } = useI18n();
formatDate(subscription.current_period_end, { dateStyle: 'medium' });
```

Never concatenate. `t('completed') + count + t('lessons')` cannot be made to
read correctly in Russian; interpolation and plural categories can. The same
applies to English plural suffixes — `` `${n} lesson${n === 1 ? '' : 's'}` `` is
untranslatable by construction, and there are none left in the app.

### Modules that are not components

Logic modules have no locale, so they emit **keys, not sentences**, and the
component that renders them resolves the key:

```js
// recommendations.js — pure logic, no locale
{ reasonKey: 'dashboard.reasonWeakest', reasonVars: { topic, percent } }

// Dashboard.jsx — has a translator
{t(rec.reasonKey, rec.reasonVars)}
```

The same pattern covers `rankKeyFor()` in the mastery engine, achievement copy,
and toasts raised from `UserStateProvider`.

### Toasts

`ToastProvider` sits *outside* `I18nProvider` — it has to, because
`UserStateProvider` raises toasts and the locale preference lives in user state.
So callers pass `titleKey` / `messageKey` / `vars`, and `ToastViewport`, which is
mounted inside the i18n context, resolves them at render time. A toast raised
before a language change displays in the new language.

## 5. Adding a string

1. Add the key to `locales/en.js`, in the namespace for its surface.
2. Add it to `az.js` and `ru.js`.
3. Use `t('namespace.key')`.

`src/i18n/i18n.test.js` fails if a locale is missing a key, has a key English
does not, leaves a value empty, or uses different interpolation variables from
English. That check is why step 2 cannot quietly be skipped.

### Pluralisation

A counted string is an object keyed by CLDR category:

```js
// en — two forms
lessonCount: { one: '{count} lesson', other: '{count} lessons' },

// ru — needs one/few/many: 1 урок, 2 урока, 5 уроков, 21 урок
lessonCount: { one: '{count} урок', few: '{count} урока', many: '{count} уроков', other: '{count} урока' },

// az — the noun stays singular after any numeral: 1 dərs, 5 dərs
lessonCount: { one: '{count} dərs', other: '{count} dərs' },
```

Pass `{ count }` and `Intl.PluralRules` selects. The test enforces that every
Russian counted entry supplies `one`, `few` and `many`.

## 6. Azerbaijani dates and numbers are formatted here, not by `Intl`

`core.js` formats `az` dates and numbers directly. This is not a stylistic
preference and should not be "simplified" back to `Intl`.

Several runtimes — including the Chromium this project previews in — report `az`
as supported while shipping no Azerbaijani patterns. `supportedLocalesOf` returns
`az-AZ`, `resolvedOptions().locale` says `az-AZ`, and then `Intl` silently
returns the root fallback:

| | Reduced ICU (observed) | Correct |
| --- | --- | --- |
| 14 March 2026 | `2026 M03 14` | `14 mart 2026` |
| 12345 | `12,345` | `12.345` |

A runtime with full ICU (Node 24 here) gets it right, which is exactly what makes
the failure easy to miss: whether a learner saw `2026 M03 14` depended on their
browser build, not on our code. Azerbaijani date and number formats are simple
and stable, so producing them directly is both shorter than detecting the broken
output and correct everywhere. English and Russian have dependable data and keep
using `Intl`.

## 7. What is never translated

**Code.** Identifiers, method names, property paths, error class names, URLs and
CLI commands stay exactly as they are. `Array.prototype.map()` is
`Array.prototype.map()` in every language. When a runtime error name appears in
copy it is interpolated, not translated: `t('learning.runFailed', { error: 'TypeError' })`.

**Stable internal values.** Only display labels are translated:

| Stays | Translated |
| --- | --- |
| `difficulty: 'beginner'` | "Beginner" / "Başlanğıc" / "Начальный" |
| `status === 'canceling'` | "Canceling" / "Ləğv edilir" / "Отменяется" |
| `plan: 'pro'` | shown as "Pro" everywhere |
| content ids, slugs, `topicIds`, track ids | their labels |

Every enum in `src/content/schema/types.js` exposes a `*_KEY` map — `DIFFICULTY_KEY`,
`TRACK_KEY`, `MASTERY_KEY`, `INTERVIEW_KIND_KEY`, `INTERVIEW_LEVEL_KEY`,
`PLACEMENT_DOMAIN_KEY`, `PLACEMENT_LEVEL_KEY` — that points at a dictionary key
rather than holding English. Entitlement logic compares literal tokens, so it is
locale-independent by construction. A gate passes a `kind` token — `challenge`,
`project` — and the wall builds its own sentence from it.

**Established developer terminology**, where that is what the audience actually
reads: JavaScript, DOM, API, Promise, async/await, callback, closure, scope,
prototype, array, object, function, fetch, HTTP, JSON, `localStorage`, Map, Set,
RegExp, Big O, event loop, Google, GitHub, OAuth, Pro, Free, XP, Playground,
snippet, worker. "Замыкание" is correct Russian, but a Russian-speaking developer
reads `closure`; forcing the translation makes the interface less clear, not more.

A curriculum **track name** is the counterpart to that rule and *is* translated:
it sits beside "Основы" and "Браузер и DOM" in the sidebar, so a bare English
word there reads as an untranslated string rather than as terminology. Both
halves of the rule have a test.

## 8. Persistence and account switching

The locale lives in the existing settings slice (`state.settings.locale`), so it
persists in local storage for guests and rides the normal cloud sync for
signed-in learners. No new table, and nothing in billing or subscription data.

It is a display preference. Importing a progress file can set it, and that is
safe — the same import cannot affect plan, entitlement, subscription or identity,
which is enforced separately and tested in `premium-delivery.test.js`.

## 9. Accessibility

`I18nProvider` sets `document.documentElement.lang` whenever the locale changes,
so assistive technology announces the right language and the browser hyphenates
correctly. Accessible names, dialog labels and screen-reader-only text all go
through `t` like any other string, and `i18n-surfaces.test.jsx` asserts a few of
them directly so a page cannot end up visually translated with English aria
labels.

**The content-language boundary.** Authored content is English inside a document
declared `az` or `ru`, so it is marked `lang="en"` at the point it is rendered.
Without that, two things break: a screen reader announces English prose with
Azerbaijani or Russian phonetics, and `text-transform: uppercase` — which is
language-sensitive — renders the authored word "Orientation" as "ORİENTATİON"
under `lang="az"`, corrupting the source text through presentation.

The marking is applied per string, never per region: `lang` is inherited, so
marking a whole panel English would relabel the translated buttons inside it —
the same bug pointing the other way. Two shared boundaries carry it:

| Boundary | Covers |
| --- | --- |
| `InlineMarkup` | all authored prose (70 call sites, unchanged) — wrapped in one `<span lang="en" class="min-w-0 flex-1">`. It must generate a box: see `docs/CONTENT-PROGRESS.md` on the text-fragmentation defect. |
| `Authored` | plain authored strings: titles, API names, categories, topic labels, milestone names |

`Diagram` marks its whole `<figure>`, because a diagram is educational content
end to end and contains no translated chrome. `HighlightedCode` marks its
`<pre>`, since rendered code is canonical English and is the text most damaged by
foreign-language pronunciation.

Where a translated label and an authored value sit in one chip, only the authored
half is marked:

```jsx
<Badge tone="primary">
  {t('learning.moduleNumber', { order })} · <Authored>{module.shortTitle}</Authored>
</Badge>
```

`src/tests/content-language.test.jsx` (21) proves both directions: authored
titles and prose resolve to `en` in az and ru, translated chrome beside them
still resolves to the UI locale, no chrome control is marked English, and
entitlement, ids and content are unchanged.

## 10. Validation

| Check | What it proves |
| --- | --- |
| `src/i18n/i18n.test.js` (36) | the three dictionaries agree on keys, values and interpolation variables; plural categories; Azerbaijani date/number formatting; that stable tokens are untranslated |
| `src/tests/i18n-ui.test.jsx` (30) | the plumbing: default, fallback, persistence, `<html lang>`, immediate switching, and that changing language writes *only* the locale |
| `src/tests/i18n-surfaces.test.jsx` (45) | every migrated screen, in az and ru: correct wording, and no leaked key |
| `src/tests/content-language.test.jsx` (21) | the content-language boundary: authored content declares English, translated chrome does not |

The raw-key check in `i18n-surfaces` is deliberately precise. It flags dotted
text only when it **resolves to a real dictionary entry**, because that is what a
leak looks like and what authored prose never accidentally is — a page rendering
"returns undefined" or `${userInput}` from a challenge prompt is content, not a
bug. The blunt version produced only false positives; this version catches the
bug that actually shipped once, when Bookmarks rendered the literal
`{t('bookmarks.emptyBody')}` to users.

## 11. Adding a locale

1. Create `locales/<code>.js` with every key from `en.js`.
2. Add the code to `SUPPORTED_LOCALES`, `LOCALE_NAMES` (in its own language) and
   `INTL_LOCALES` (a BCP 47 tag) in `core.js`.
3. Import it into `DICTIONARIES` in `index.jsx`.
4. Check that `Intl` really has data for it (see §6) before trusting the
   formatters.
5. Run the tests — the validation will list anything missing.

Nothing else needs to change. Routes carry no locale prefix, so bookmarks, deep
links, OAuth redirects and Gumroad return URLs are unaffected by language.
